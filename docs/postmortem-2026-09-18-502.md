# 事故复盘：2026-09-18 aishield.tools 全量 502（约 20.5 小时）

- **影响窗口**：2026-09-17 05:01Z → 2026-09-18 01:31Z（`last_healthy_at` 到恢复部署，约 20 小时 30 分）
- **症状**：`https://aishield.tools/*` 全部 502（`Server: cloudflare`，`CF-RAY: ...AMS`，响应体 `error code: 502`）
- **根因一句话**：`api/server.py` 的 `assert_not_root()` 拒绝 root 身份，而 VPS 上的部署身份**就是 root**，部署链路从未设置 `AISHIELD_ALLOW_ROOT=1` → API 进程启动即 `sys.exit(2)` → `:8450` 无监听 → cloudflared tunnel 活着但后端空转 → Cloudflare 回 502。

> 本文件同时补记两条提交说明：`7f1670a6`（`scripts/deploy-named-tunnel.sh`）与 `83e7672a`
> （`.github/workflows/self-heal-closed-loop.yml`）的 commit message 在推送时被本机 bash 包装层
> 吃成了字面 `-m`。文件内容完整落地，只有 message 丢失，此处为权威记录。

## 1. 为什么「看起来在自愈」却挂了一整天

VPS 侧 `cloudflared` 进程全程存活（PID 1326118），tunnel 正常向 Cloudflare 握手，
DNS/CNAME/证书全部有效。所以这不是网络、DNS、证书或 tunnel 问题——
是**后端进程从来没起来过**。

三次自动自愈（09-17 11:53 / 17:09 / 21:31 UTC）的 STEP 8 都打印了：

```
--- API (localhost:8450) --- FAIL
```

但每一步都以 `success` 结束。三层假绿叠加，使故障完全不可见：

| # | 假绿来源 | 机制 |
|---|---|---|
| 1 | `ssh ... \| tail -60 \|\| echo "REPAIR_SSH_FAILED"` | 管道让 step 退出码取自 `tail`，SSH 断连与部署失败都被吞成 success |
| 2 | `deploy-named-tunnel.sh` 结尾无条件 `exit 0` | API 状态 FAIL 也报成功，job 结论恒 success |
| 3 | `tail -40` 截掉 STEP 1 | 故障恰在 API 启动段（STEP 1），启动输出从未出现在任何日志 |

叠加第 4 层：**escalate 只判 `test`/`verify`**。repair 失败时 test 与 verify 都是 `skipped`
（不是 `failure`），所以 `escalate` 一次都没触发过——修复环节挂了，没有任何告警。

以及第 5 层：**`git pull` 同步的是陈旧代码**。VPS 到 github.com 网络不通，
fetch 失败被吞掉后 reset 到本地陈旧的 `origin/main` 引用。也就是说，
「自愈」跑的是 VPS 磁盘上的旧 `deploy-named-tunnel.sh`——**用旧代码修旧代码**。

## 2. 根因定位过程

1. `data/state/health.json`：`last_healthy_at=2026-09-17T05:01Z`，`consecutive_failures=5`
2. 夜间接警报告 `eco/reports/guard-2026-09-18.md` 确认约 20h 停机
3. 拉取 4 次 workflow run 日志（`35277111476` / `35250963211` / `35293632298` / `35293760628`）
4. `35293760628` 的 repair artifact 里出现了真正的原因：

```
AIShield refuses to run as root.
...
UID: 0
```

`assert_not_root()` 在 `api/server.py:2562`（2026-09-16 引入，借鉴 KeygraphHQ/shannon #323）
会 `sys.exit(2)`；而 systemd、`systemctl` 都必须 root——**部署身份天然是 root**，
而整条部署链路没有任何一处设置 `AISHIELD_ALLOW_ROOT=1`。

5. 交叉验证：`cloudflared` 进程活着 + `:8450` 无监听 → 锁定「tunnel 在 / 后端不在」，
   排除 DNS/tunnel/证书分支。

## 3. 顺带修掉的三个真实缺陷

修根因之外，脚本本身还有三处会持续制造故障的结构性问题：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| API 进程只有 `nohup`，没有进程守护（cloudflared 却有 systemd + cron 双重） | API 挂一次就永久静默，无重启、无告警 | 新增 systemd `aishield-api`（`Restart=always`）+ `install_api_service()` + `ensure_api_up()` 三轮重试与全量诊断 |
| STEP 6 用 `pkill -f "cloudflared"` 停 tunnel | VPS 是多项目机（aishield-tunnel / healthlens / healthlens-tunnel），一刀切会杀掉**别的项目的 tunnel** | 改为按 PID 文件精确停 + `systemctl stop cloudflared-tunnel`（兜底 `pkill -f '\.cloudflared/config\.yml'`） |
| STEP 6 的 `nohup` 实例与 STEP 7 的 `systemctl restart` 实例同时持有同一 tunnel ID | Cloudflare 连接抖动，日志 `ERR no more connections active and exiting` | STEP 7 前先杀掉 nohup 实例并清 pidfile；cron 行改成 `curl -sf :8450/api/v1/health \|\| /opt/start-tunnel.sh`（探活而非探进程名） |

另有：cron 存活检查原来是 `pgrep -f 'cloudflared tunnel'`，会被**别的项目的** tunnel 满足——
false-live，本项目挂了也不触发拉起。

## 6. 恢复后补查：同形状的第 5 层假绿

恢复之后复查「两条部署路径的退出码是否真的会红」时，在另一条路径上找到了
同形状但还没咬人的第 5 层：

`.github/workflows/deploy-server.yml` 的 "Deploy via SSH" 远端脚本结尾是

```
bash scripts/deploy-named-tunnel.sh 2>&1
echo "DEPLOY_EXIT_CODE=$?"
```

`echo` 的退出码恒为 0，而它是远端脚本的**最后一条命令** —— 于是远端脚本整体
退出码恒为 0。本轮给 `deploy-named-tunnel.sh` 新增的「API 不健康即 `exit 1`」
会被这句诊断输出吞掉，deploy job 照样报 success。

前四层让故障不可见，这一层会让**修复本身**的失败不可见。它之前没暴露，是因为
那时候部署脚本还是无条件 `exit 0`，两边都是绿的，看不出谁在骗谁；本轮把
部署脚本改对了，这一层才从「无害」变成「吞掉新加的失败信号」。
修好一处假绿之后，下一处会立刻顶上 —— 所以要顺着同形状往下查，而不是查到绿就收手。

修法：

```
set -o pipefail
bash scripts/deploy-named-tunnel.sh 2>&1
rc=$?
echo "DEPLOY_EXIT_CODE=$rc"
exit $rc
```

并把这类形状钉成契约测试：`tests/test_deployment_observability.py`（14 条断言），
含一条自否证——把上面的历史反模式原样喂给检测器，必须报出第 3 行。
同一测试文件还钉住 `self-heal-closed-loop.yml` 的六条不变量：`pipefail`、
`rc=$?`、`exit $rc`、`tee` 全量落盘（禁止 `| tail -60`）、repair 日志 artifact、
`escalate` 必须覆盖 `repair`；以及两条部署路径都必须 tarball-first。

配套的 `tests/test_deployment_root_guard.py`（6 条断言）钉住第 1 层根因：
每个启动 `api/server.py` 的位置都必须设置 `AISHIELD_ALLOW_ROOT=1`，
禁止按进程名杀 cloudflared，cron 探活必须走 HTTP。

## 8. 经验

- **安全护栏加在启动路径上时，必须同时核对部署身份。** `assert_not_root()` 本身完全正确——
  错的是把它合进主干时没人看部署用的用户。护栏一旦与部署身份冲突，结果是 20 小时静默停机
  而不是启动失败告警，因为「进程没起来」不等于「进程崩了」。
- **假绿的代价比假红高一个量级。** 五层假绿叠加，让三次自愈全部报告成功。
  堵法固定三条：脚本不吞退出码、传输层失败不退化成空值、门禁必须断言被请求的路径。
- **多项目共机时，禁止用进程名做杀进程的依据。** `pkill -f` 在这台机器上会误伤邻居项目，
  而 cron 用进程名做探活会被邻居骗过。必须落到 PID 文件 + HTTP 探活。
- **同一个后端不要有两个进程实例。** nohup + systemd 双写同一 tunnel ID，
  Cloudflare 会表现为连接抖动而不是明确报错。
- **诊断语句和退出码是两件事，混用就是第 6 节那种假绿。** 「打印出结论」和
  「传出结论」在 shell 里是两条命令，前者不改退出码。凡是 `echo ... $?` 之后
  没有紧跟 `exit`，上一条命令的失败就丢了。
- **写契约测试时，注释里的字面量也会骗过断言。** 工作流用注释记录「旧写法是什么、
  为什么错」是好事，但 `REPAIR_SSH_FAILED`、`| tail -60`、`AISHIELD_ALLOW_ROOT=1`
  这些字面量会让朴素的子串断言误报/漏报。子串检查必须先剥注释（尊重引号），
  否则得到的是一份「看着很严、实际什么都没拦」的门禁。
- **查假绿要顺形状往下查，不能查到绿就收手。** 把部署脚本的 `exit 1` 修对之后，
  第 5 层立刻从无害变成「吞掉新加的失败信号」。假绿是群居的。
